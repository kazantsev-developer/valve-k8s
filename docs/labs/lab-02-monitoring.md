## Три столпа наблюдаемости (Observability) и Алертинг

Наблюдаемость - это способность системы предоставлять данные о своём внутреннем состоянии на основе внешних сигналов. В рамках лабораторной работы развёрнут комплексный комбайн из четырёх взаимосвязанных компонентов, развёрнутых в кластере Kubernetes с помощью Helm-чартов.

## 1. Метрики (Prometheus + Grafana)

Метрики отражают общее здоровье и производительность системы в виде числовых агрегированных показателей. Архитектура построена на базе паттерна `RED` (`Rate`, `Errors`, `Duration`):

- Rate (Пульс системы): количество входящих запросов в секунду (`RPS`). Мониторит интенсивность трафика.
- Errors (Осложнения): процент ошибочных ответов (`5xx статус-коды`) от общего числа запросов.
- Duration (`Latency / Скорость реакции`): Время обработки запросов, рассчитываемое через `перцентиль p95`. Позволяет отсекать единичные выбросы и видеть реальную скорость ответа для 95% пользователей.

Для автоматического обнаружения сервиса и сбора метрик `Prometheus` использован объект `ServiceMonitor`. Он декларативно указывает Prometheus-оператору скрейпить (собирать) данные с эндпоинта `/metrics` нашего приложения каждые `5 секунд`.

## 2. Логи (Loki + Grafana Alloy)

Логи представляют собой упорядоченный во времени текстовый поток событий, дневник приложения.

- Формат сбора: приложение на Go использует структурированное логирование через пакет `slog` в формате `JSON`.
- Архитектура доставки:по схеме `DaemonSet` на каждой ноде кластера развёрнут легковесный агент `Grafana Alloy`. Он собирает сырые логи с файловой системы контейнеров хоста и стримит их в централизованное хранилище `Loki`.
- Контекст инжекции: в каждую строчку лога динамически вшивается уникальный идентификатор запроса `trace_id`, что связывает текстовые события с распределённой трассировкой.

## 3. Трейсы (OpenTelemetry + Jaeger)

Распределённая трассировка `Tracing` - это рентгеновский снимок пути прохождения одного конкретного запроса через все функции кода и микросервисы.

- Инструментарий: в рантайм Go-приложения встроен `OpenTelemetry SDK`. При поступлении HTTP-запроса создаётся корневой `Span`, отрезок времени.
- Сшивание с логами (Сквозная навигация): в панели `Grafana` через механизмы интеграции `Loki` настроена связь. Идентификатор `trace_id` из строчки лога автоматически превращается в кликабельную ссылку. При клике на неё инженер мгновенно проваливается в `Jaeger-интерфейс` и видит визуальный таймлайн выполнения запроса на уровне функций кода, локализуя причину тормозов или ошибок без ручного поиска.

## 4. Оповещения (Alertmanager + Karma)

Система проактивного уведомления избавляет инженера от необходимости непрерывного ручного контроля графиков.

- Логика Prometheus Rules: оповещения срабатывают на основе математических выражений над метриками. Настроены три правила тревоги: высокий процент ошибок (`Error Rate > 5%`), высокая задержка ответа (`p95 Latency > 1s`) и полное отсутствие подов (`клиническая смерть сервиса`).
- Alertmanager: принимает сигналы тревоги от Prometheus, группирует дубликаты, чтобы исключить лавинообразный спам, и маршрутизирует их в приёмники (`Webhook-приёмники` или `тупиковый Null-роут` для `Watchdog-алертов`).
- Dashboard Karma: используется как продвинутый визуальный пульт дежурного инженера. `Karma` агрегирует данные из `Alertmanager`, предоставляет гибкую фильтрацию и отображает карточки активных инцидентов с точными формулировками причин аварий.

Инженерные выводы для проекта `Valve`
Традиционный `cAdvisor` собирает RED-метрики с задержкой в `10–15 секунд` снаружи контейнера. Если под ловит резкий всплеск нагрузки, алерты в Alertmanager сработают с огромным опозданием, когда сервис уже получит `OOMKilled`.
Это обосновывает цель создания Valve: `собирать показатели аллокаций памяти и горутин через eBPF из ядра за микросекунды до того, как cAdvisor успеет их зафиксировать снаружи, выполняя роль моментального автоматического предохранителя ресурсов`.
