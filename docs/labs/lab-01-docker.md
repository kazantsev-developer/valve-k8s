## Фундаментальный принцип контейнеризации

Контейнер не является виртуальной машиной или изолированной ОС. Контейнер это `стандартный процесс` в пространстве пользователя (user space) ядра Linux, для которого на уровне ядра применены три механизма ограничения: пространства имен `namespaces`, контрольные группы (cgroups) и ограничение системных полномочий (capabilities/seccomp).

## 1. Изоляция окружения (Linux Namespaces)

Механизм `namespaces` изолирует системные ресурсы процесса, создавая для него обособленную виртуальную карту местности. В работе применена команда утилиты `unshare` для разделения следующих пространств:

- PID Namespace (Процессы): изолирует таблицу процессов. Запущенная командная оболочка bash внутри кокона получает `PID 1`, становится прародителем дерева процессов данной подсистемы.
- Нюанс реализации: для корректной работы утилиты `ps aux` требуется принудительное перемонтирование виртуальной файловой системы процессов `mount -t proc proc /proc`. Без этого утилита пытается читать хостовый путь `/proc/self` и завершается с ошибкой.
- NET Namespace (Сеть): полностью изолирует сетевой стек. Внутри контейнера исчезают физические интерфейсы хоста, остаётся только петлевой интерфейс `lo` (loopback). Процесс находится в полном сетевом вакууме.
- UTS Namespace (Имя хоста): позволяет изменять имя хоста `hostname` внутри изолированного пузыря без изменения системного имени основной машины.
- USER Namespace (Пользователи): реализует великую иллюзию власти. Внутри изолированной среды пользователь обладает полными правами суперпользователя (root с UID 0), однако для внешней хост-системы этот же процесс выполняется от лица обычного бесправного пользователя (ubuntu с UID 1000), что предотвращает риски компрометации ядра хоста.

## 2. Ограничение ресурсов (Cgroups v2)

Контрольные группы ядра Linux задают жесткие лимиты на потребление ресурсов. Память является несжимаемым ресурсом: при превышении лимита (например, `memory.max`) срабатывает `OOM Killer` и процесс уничтожается сигналом `SIGKILL`. Процессор - сжимаемый ресурс, где при достижении лимита `cpu.max` включается `CPU Throttling`, замедляя работу без завершения процесса. Лимиты процессов `pids.max` защищают ноду от `Fork-бомб`, блокируя системные вызовы при превышении порогов.

## 3. Системные привилегии (Capabilities и Seccomp)

`Linux Capabilities` позволяют дробить права суперпользователя (например, отключение `cap-drop=SYS_TIME` запрещает менять системные часы). `Seccomp` применяет списки разрешенных или запрещенных системных вызовов на уровне ядра, блокируя нежелательные действия вроде создания директорий через `mkdir`.

## 4. Сравнение самодельного скрипта и промышленного Docker

Самодельный скрипт запускает процессы в текущем окружении хоста без изоляции файловой системы и сети. Docker обеспечивает полноценную изоляцию через `chroot` и `pivot_root`, управляет сетевым стеком через мосты и `iptables`, оптимизирует хранение с помощью слоев `OverlayFS` и координирует жизненный цикл через `containerd`.

## 5. Оптимизация образов (Multi-stage Builds)

Многоэтапная сборка `Multi-stage builds` отделяет среду компиляции от финального исполнения, позволяя создавать минимальные образы на базе `scratch`. Для сохранения данных между перезапусками эфемерных контейнеров используются независимые `Docker Volumes`.

## 6. Предел контейнерной изоляции и gVisor

Стандартные контейнеры разделяют ядро с хостом, что несет риски при уязвимостях. Технология `gVisor` добавляет прослойку в виде `виртуального мини-ядра Sentry`, которое перехватывает системные вызовы и исключает прямой контакт контейнера с хостовым ядром.

## 7. Нюансы Observability на macOS (Ограничения cAdvisor)

В средах macOS (`OrbStack`, `Docker Desktop`) метрики троттлинга `CFS` могут быть недоступны из-за виртуализации. В качестве альтернативы мониторинга нагрузки используется отслеживание системного времени процессора через `container_cpu_system_seconds_total`.
